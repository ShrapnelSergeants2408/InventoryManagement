## Findings (all fixed in this review unless noted)

1. **A long-open editor could save vendor changes after relocking.** Once the vendor fields were opened, Save didn't ask again, even after the timer or the lock button had relocked. Vendor changes are now saved only while unlocked, and the PIN is asked again otherwise. Browser checks were added for "relocked while editing asks again" and "…and with the PIN it saves". The Settings screen had the same gap for unsaved changes; that case is now covered by a browser check.
2. **Test gap: whole-hash comparison.** A mutant that compared only the first byte of the hash passed, since a wrong PIN almost always differs there. A test now changes only the last byte, and the mutant is caught.
3. **Test gaps: alphabet coverage, restarting the timer, and Change PIN validation.** Tests were added for every alphabet character appearing in recovery codes, a second unlock restarting the timer, and `savePin` refusing a bad PIN.
4. **Setup logo** lacked the white circle shown in mockup 9f. Fixed.
5. **Q2 is partly resolved.** A tablet whose storage was *cleared* now opens normally and goes through PIN setup, after which a mentor can restore from Backup. A database that **can't be opened** still has no in-app way back. That path stays with M10, together with the restore choice in first-launch setup.
6. **Open, minor:** a dialog opened after the PIN (supplier, category or location rename/remove; Change PIN) can still be saved if the tablet relocks while it is open. These dialogs are short and modal, and the editor and Settings, which can stay open for a long time, re-check. Accepted as accident prevention (§6).
7. **Open, minor:** the wrong-try count is shared by PIN and recovery-code tries, so "n wrong tries so far" counts both. This is deliberate: one 30-second wait covers both ways in.

## Decisions made while building (within the approved defaults)

- **Setup comes before the app whenever no PIN is stored.** That covers a new tablet, a tablet from before M6, and cleared storage. M6 has two steps, PIN and recovery code. The starter catalog still loads by itself at boot until M10 adds it as step 3, with the restore choice (Q2).
- **The PIN is typed twice** at setup, at Change PIN and at recovery. Mockup 9f shows one entry; typing twice avoids locking the team out with a typo.
- **The recovery code is 10 characters, shown as two groups of 5** (D6). Mockup 9g shows 12 in groups of 4. Typing ignores capitals, spaces and the dash.
- **Nothing is saved until "I wrote it down"**, both at setup and at recovery. A code that was never written down never replaces the old one.
- **Settings ranges:** reminder 1–60 days, stale-price age 7–365 days, unlock length 1–30 minutes. A new unlock length applies from the next unlock.
- **Opening the item editor while unlocked opens its vendor fields** (mockup 3b). Saving vendor changes still needs the tablet to be unlocked at that moment (finding 1).
- **Anyone can read the settings and use "Forgot the PIN?"** The recovery code is the protection there.

## Remaining uncertainty

- **Medium:** one PBKDF2 check at 100,000 iterations measured about 26 ms in Node on this PC. The Tab S8 is slower but should stay well under a second; untested (Stage 5).
- **Low:** the PIN pad's keyboard support is for a hardware keyboard. The on-screen keys are the main input, and the Android soft keyboard never opens for the pad.
- **By design (§6):** this is accident prevention. Anyone with Chrome DevTools can clear the stored hash or read IndexedDB.
