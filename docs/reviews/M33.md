With its file blocked (DevTools `Network.setBlockedURLs`, service worker bypassed), History says "Couldn’t open this screen" (role alert) with **Reload the app**, and the rest of the app still works. Unblocked, going back opens it, because Chrome tries the load again. With Settings blocked, **Reload the app** reloads the page and the screen opens.
- Full `npm run checks`: **972 pass across 33 scripts, no console problems** (389 s), first run, before the m33 check was added. m33 then ran on its own (7 pass).
- Start-up time (outside the repo), 1.7.1 and 1.7.2 built and measured back to back: reload until the inventory list is drawn, median of 5.

  | | 1.7.1 | 1.7.2 | 1.7.2 again |
  |---|---|---|---|
  | Full CPU | 182 ms | 184 ms | 185 ms |
  | CPU ÷ 4 | 469 ms | 574 ms | 434 ms |

  **No measurable difference.** The spread between the two 1.7.2 runs is larger than any gap to 1.7.1. Repeated reloads probably reuse the browser's compiled code, so parsing less JavaScript saves nothing here. A true cold start (first launch on a new device) might gain a little, but that wasn't measured. R8's value is structural, not a speed-up you'd feel: JSZip and the backup code are off the start-up path, the large-chunk warning is gone, and future screens can be added on demand.

## Details for Dan to confirm
- (a) **On-demand screens are fetched 1.5 s after the inventory opens**, so they open instantly afterwards. Opened sooner, a screen shows a blank moment while its file loads (from the offline cache, so a few milliseconds).
- (b) **The helper app and first-time setup load on demand too.** A helper phone never runs the shop tablet's on-demand screens, though the service worker still downloads every file once so the app works offline. So the first download is the same size as before; what shrinks is the code each device parses at start-up.
- (c) **Not split:** the Order screen's Export dialog (Papa Parse, 19 kB), and the scanner (already loaded on demand since M10).
